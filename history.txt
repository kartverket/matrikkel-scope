* SModelAction, SModelButton are enabled with the bound parameter is not null, and if the bound parameter is a boolean/Boolean, then
  they are enabled if the bound value is not null and true. (ludovicc)
* Added get(String key, String defaultValue) to UIStrings (ludovicc)
* Added support for default buttons from SwingView and SPanel - with method setDefaultButton (ludovicc)
* Fixed behaviour of STextField regarding how VK_ENTER events are handled, made it similar to JTextField.
This means that if a STextField has no control id, then pressing Enter will activate the default button on the screen. (ludovicc)

0.6.0
18/8/01

This is a formal release of the recent refactoring work,
particularly on the model and swing implementations.

The big news is:
* The Swing implementation is more complete and actually works now,
  being backed up with a suite of unit tests.
* The model implementation is decoupled and less intrusive than it used to be. 
  Users of the framework can now decide whether to use standard Javabean
  model objects that are not linked into Scope's model implementation,
  or to use Scope's BasicModel base class to implement models that tie in
  more closely. The former choice means that Swing GUIs need to be told
  to refresh() manually when their bound model changes state, while the
  latter allows fully automatic two-binding.
  
NB: Changes to public API! See below.

The new implementation also opens the way to alternative model 
implementations, for example to allow JMX MBeans to plug into the 
framework.

Note that in this release, the BasicModel implementation is still broken
such that ModelChangeEvent despatch will probably fail for BasicModel
subclasses that implement equals() and/or hashcode(). This is now
very high on the list of things to fix.
  

Changes: (see also the change list for release 0.6.0pre1 below)
* Rename of Swing components to sensible naming scheme.
* Rename and repurpose Model to ModelChangeEventSource.
* Remove SelectorIterator in favour of standard Iterator implementations.
* Tidy of all imports.
* Tutorials in sync with current state of sources.
* Documentation in sync with current state of sources (though a little incomplete).
* Convenience methods for setting up Selectors on Swing widgets using String descriptions.
* Lots of tidying up.

Details of API changes: (see also the change list for release 0.6.0pre1 below)
* Replace "BoundLabel" with "SLabel".
* Replace "CheckBox" with "SCheckBox".
* Replace "List" with "SList".
* Replace "ListCellRenderer" with "SListCellRenderer".
* Replace "ListModel" with "SListModel".
* Replace "Panel" with "SPanel".
* Replace "SingleListSelection" with "SSingleListSelection".
* Replace "TextArea" with "STextArea".
* Replace "TextField" with "STextField".
* Replace references to "Model" with "ModelChangeEventSource".
* Replace uses of "SelectorIterator" with "java.util.Iterator" that iterates over Selectors.



0.6.0pre1
12/8/01

NB: Changes to public API! See below.

This release can be considered a bug-fix release for those using earlier
0.5.x versions. However, in reality it represents work in progress that
will soon result in a full 0.6.0 release, featuring a heavily refactored internal
implementation and a much simpler and more flexible public API.

Changes:
* Addition of more Swing example applications.
* Bug fixes in servlet implementation.
* Major reworking of model properties, actions and editors/viewers around decoupled
  ModelManagers. This change deprecates methods in BasicModel concerned with
  properties and actions.
* Added full support for JavaBeans indexed properties in the default PropertyManager.
* Reworked Selectors including some API changes (see below).
* Major reworking of Swing implementation including addition of unit test suite. This
  involves some changes to the public API (see below).
* Added better error handling: assertions are now used only to test internal integrity
  of the framework and RuntimeExceptions are used in validating paramters to
  the public API.
* Added support for java.util.List and Object[] as models.
* Removed most of the Model interface which may disappear or turn into a 
  ModelChangeEventSource interface.
* Removed most of BasicModel to follow the Model interface.
* Removed the need for application developers to initialise the Swing ViewContext.
* Started reworking the documentation to match the current implementation, and to 
  provide a simple introduction to the use of Scope rather than details of its internals.

Details of API changes:
* Replace SelectorFactory.createFromSelectorDescription(String) with Selector.fromString(String).
* Replace SelectorFactory.get(String) and SelectorFactory.getConstant(String) with Selector.fromString(String).
* Replace SelectorFactory.get(int) with Selector.fromInt(int).
* Replace List.setTextSelector(Selector) with List.setRendererSelector(Selector)
* Replace List.setIconSelector(Selector) with List.setRendererIconSelector(Selector)
* (Optional) Remove setup of ViewContext from Swing applications:
        ViewContextFactory.getInstance().setGlobalContext(new SwingContext());
  This is now done automatically when a SwingView is created.
* BasicModel and Model have been severely pruned. See PropertyManager, ActionManager
  and EditorManager for replacements. I can't imagine this affects anyone using
  Scope to build applications, but I know it impacts some extensions built on top of Scope.
* Replace overrides of BasicModel.isPropertyReadOnly(Selector) with an implementation
  of org.scopemvc.model.beans.DynamicReadOnly.

0.4.0
19/6/01
A long-awaited major release of Scope following a prolonged 
sequence of 0.3.X releases.  This distribution includes: a Model class 
based on the standard JavaBeans API; much improved Controller and View 
management; more complete unit tests; better documentation; and many bug 
fixes.  It includes work by the project's newest contributor, Simon 
Harris.  Scope is now offered under a BSD style license to simplify the 
legal issues around commercial use.  

The distribution includes an incomplete view implementation for Swing GUIs 
and a full view implementation for servlet applications based on XML/XSLT.  
Both implementations offer transparent round-trip data-synchronization 
between Model and View, and enable very consistent styles of coding that 
hide the details of the application context from the developer.  

Scope has been used successfully in developing commercial web applications 
and has been used as a basis for development of alternate UI layers 
including VoiceXML.  

Future releases of Scope will move the concept of a generic MVC implementation 
forward in some huge steps. Watch for news of future plans on the web site...
this will be very cool!

0.2.0
17/12/00
This represents a major release that includes a 
sample file-browser application written using 
Scope in a Swing context. Although a very 
simple demonstration, the sample sources are 
worth examining -- I believe they demonstrate 
how effective the Scope framework is in simplifying 
GUI development and in partitioning presentation, 
application and business logic. Most of the source 
code lies in the Model classes that build a simple 
JavaBeans model to represent the filesystem. The 
application itself is relatively trivial.

The binary distribution includes an executable jar 
that runs the filebrowser.

A proof of concept of a servlet implementation is 
hidden in the source distribution. Although not ready 
for real use, this code has proved that it will be 
possible to take a Swing-based application built on 
Scope, and port it to a web-based application by 
simply replacing the views.

The core APIs are now almost frozen. I had hoped 
for a more complete freeze but I've found that I can 
convert the CollectionModel APIs into a simple generic 
infrastructure that will enable View components that 
handle collections in a generic way, eg generic 
drag-and-drop. There's also some minor tidy-up that 
needs to be done to consolidate the work so far.

The next releases will concentrate on the CollectionModel 
APIs, more tidy-up of the core, and a full servlet 
implementation that will be built around XSL views. 
The aim is to allow these views to be built from 
embedded components in exactly the same way as 
conventional windowing GUI development. Ultimately, 
it should be possible to generate Swing and Servlet 
views from the same view description, perhaps 
expressed in XML.

Sometime soon I would also like to consider 
code-generation for the Model classes. I'm thinking 
of a preprocessor that will take standard JavaBeans 
classes and turn them into full Scope Models with 
ModelChangeEvent firing etc added automatically.

Summary of changes:
- Major bugfixing, refactoring and additions to the Swing View classes.
- Added more unit tests.
- Additions to Model packages to support conversion to and from character streams for the servlet implementation.
- Work on Swing-based filebrowser application.
- Work on servlet implementation.
